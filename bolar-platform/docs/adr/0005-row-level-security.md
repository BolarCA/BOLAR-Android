# ADR 0005: PostgreSQL row-level security as defense in depth (Days 91-104)

- Status: accepted (opt-in enforcement; policies always installed)
- Date: 2026-11-09
- Extends: [ADR 0003 tenant isolation](0003-tenant-isolation.md)

## Context
ADR 0003 isolates tenants in the application: `tenantDb(ctx)` injects `tenantOrgId` into every query of a
tenant-scoped model. That is one layer. A handler that reaches for the root `prisma` client by mistake, a raw query,
or a future bug in the client extension would bypass it. The blueprint lists PostgreSQL row-level security (RLS) as
the "later hardening" for exactly this case.

## Decision
1. **Policies ship with the schema.** Migration `20261109180000_rls_policies` (generated by
   `packages/db/src/rls.ts#rlsPolicySql` from the Prisma DMMF) enables RLS on every table that carries `tenantOrgId`
   (58 tables today) and creates two policies per table:
   - `tenant_isolation` for role `bolar_app`: `USING / WITH CHECK ("tenantOrgId" = current_setting('app.tenant_id', true))`.
     Tables whose `tenantOrgId` is nullable (`Template`, `TemplateVersion`, `RetentionPolicy`, `FeatureFlag`,
     `IdempotencyKey`, `AuditLog`) also admit `"tenantOrgId" IS NULL` rows: by schema convention a NULL tenant means
     a platform-global row (platform templates, global flags, platform defaults, platform-level audit entries).
   - `owner_bypass` for the role that ran the migration (`current_user`), `USING (true)`. Table owners bypass RLS
     anyway; the explicit policy keeps migrations, seeds and tests working if `FORCE ROW LEVEL SECURITY` is ever enabled.
2. **Application role.** `bolar_app` is created `NOLOGIN` with `SELECT/INSERT/UPDATE/DELETE` on all tables and default
   privileges for future tables. Staging and production create a LOGIN member and point the API at it:
   ```sql
   CREATE ROLE bolar_app_login LOGIN PASSWORD '<from secret manager>' IN ROLE bolar_app;
   ```
   `DATABASE_URL=postgresql://bolar_app_login:...@host/bolar` plus `DB_RLS_ENFORCE=1`. Migrations keep running as the
   owner role (`prisma migrate deploy` with the owner URL), never as `bolar_app`.
3. **Transaction-local tenant.** `withTenantRls(prisma, tenantOrgId, fn)` runs `fn` inside `$transaction` after
   `SELECT set_config('app.tenant_id', $1, true)`; the setting vanishes with the transaction, so pooled connections
   never leak a tenant. Superusers and table owners are not subject to RLS, which is why the proof test connects as
   a LOGIN member of `bolar_app`.
4. **Opt-in enforcement in the API.** `forTenant(client, tenantOrgId, { rls: true })` (selected by `DB_RLS_ENFORCE=1`
   in `tenantDb`) runs `findMany/findFirst/findFirstOrThrow/count/aggregate/groupBy` inside `withTenantRls` with the
   same injected where clause. Writes keep the application-level stamping; the policy's `WITH CHECK` still rejects a
   cross-tenant row at the database when the connection role is `bolar_app`. `forTenant()` without the option is
   unchanged, so every existing test and route behaves exactly as before.

## Limits (documented, not hidden)
- Enforcement needs a non-owner connection role. With the local superuser `bolar` (`Bypass RLS`), policies are
  installed but inert; the db test proves them with a dedicated LOGIN role.
- The RLS read path adds one transaction per read (one extra round trip, measured <1 ms locally). Mutations and the
  root `prisma` client used by platform routes are not wrapped; they rely on ADR 0003 plus the `WITH CHECK` policy.
- Rows with a NULL `tenantOrgId` are visible to every tenant connection by design (global rows). `AuditLog` queries in
  the API always filter by `tenantOrgId`, so platform-level audit rows never reach a tenant through the API.
- A new tenant-scoped model needs the policies too: `rls.test.ts` fails when a table has RLS disabled or when the
  committed migration differs from `rlsPolicySql()`; add a migration with the generated block for the new table.

## Verification
- `packages/db/src/__tests__/rls.test.ts`: creates `bolar_app_rls_test LOGIN ... IN ROLE bolar_app`, connects with a
  second PrismaClient and shows: no tenant rows without `app.tenant_id` (Property, Lease, Invoice, AuditLog,
  Document); only tenant A's rows with it; a cross-tenant insert fails with `row-level security`; the setting is gone
  after the transaction; `forTenant(..., { rls: true })` reads through the policy; every tenant-scoped table has RLS
  enabled and the `tenant_isolation` policy; the migration equals the generator output.
- `pnpm db:migrate:test` applies all migrations on a scratch database (roles are cluster-wide; the `DO` block is
  idempotent).

## Consequences
- Staging runs with `DB_RLS_ENFORCE=1` and the LOGIN role from day one of the hardening phase; production follows
  after one full release cycle without RLS-attributed errors (`permission denied` / `row-level security` in Sentry).
- Rollback is a config change (`DB_RLS_ENFORCE=0` and the owner `DATABASE_URL`); policies can stay installed. See
  `docs/runbooks/config-rollback.md`.
